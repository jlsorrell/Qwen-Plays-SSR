# Task 4.2 Scope-Pure Initial Driver Hardening Design

**Date:** 2026-08-04

**Status:** Approved approach; written specification awaiting review

## 1. Context

Pull request 12 merged the passive-oracle foundation through Task 4.1. The
next executable-plan slice, Task 4.2, is intended to add the Unity-free part of
initial settled-state capture: preparation and activation, initial epochs,
two-stage update authorization, neutral-input debounce, two equal complete
capture signatures, exact frame/time deadlines, and typed failure handling.

Three independent read-only preflights found that the frozen Task 4.2 text is
not safe to dispatch verbatim:

- its prescribed `PassiveDriver` declares but never assigns
  `completedInputs`, so a fresh net35 warnings-as-errors build fails with
  `CS0649`;
- after that failed compile emits its output DLL, an ordinary incremental
  rerun can incorrectly exit zero without recompiling;
- its tests do not distinguish signature equality from object identity or
  from accepting any two captures;
- its replacement test masks missing neutral, candidate, last-capture, and
  deadline resets;
- its deadline test omits unsuccessful exact-boundary and frame-overrun
  behavior;
- its exception firewall and several directive branches have no behavioral
  oracle;
- its GREEN and commit blocks are not fail-fast and do not prove exact
  worktree, index, or commit scope; and
- it introduces substantial Task 5+ attempt and terminal machinery before
  any Task 4.2 test can reach it.

The merged repository baseline is healthy. From merge commit
`97cf6da25d915073b3ce2251db26974c0afff109`, the complete Python suite passes
offline with `1822 passed, 120 xfailed, 6 xpassed`, the current C# harness
prints exactly `SSR oracle unit harness ready`, and the current net35 Core
build succeeds with zero warnings and zero errors.

## 2. Decision

Task 4.2 will be rewritten as a **scope-pure initial-driver slice**. It will
introduce only behavior that its own tests can execute. Direction attribution,
Undo, settled-step emission, expected-input completion, Restart, and the rest
of terminal lifecycle ownership remain in Tasks 5.1--5.3, where their RED
tests precede their production surfaces.

This changes task ownership, not the approved passive-capture architecture or
the final plugin contract. At the end of Task 5.3, the driver exposes the same
planned behavior. The change is when each piece enters the codebase and gains
evidence.

Two alternatives remain rejected:

1. Retaining the dormant scaffolding and merely initializing
   `completedInputs` would minimize plan edits, but it would preserve
   unexercised behavior in a strict-TDD plan.
2. Combining Tasks 4.2 and 5.1 would make the scaffolding reachable, but it
   would couple initial settling with native input attribution and create a
   substantially larger diagnostic surface.

## 3. Scope

### 3.1 Task 4.2 production scope

Task 4.2 may add or change only the production state needed for these paths:

1. validate constructor inputs;
2. write the Run record during one-shot preparation;
3. activate from `Disabled` to `AwaitGame` only after preparation;
4. start, reset, and rebase an initial epoch;
5. observe a balanced player-poll scope solely to establish neutral versus
   cardinal physical input during the initial epoch;
6. issue, authorize, rebase, complete, or fail one update directive;
7. enforce `state -> time -> path -> state -> authorization -> gate ->
   capture -> UTC -> completion` ordering;
8. require two distinct eligible update callbacks whose complete capture
   signatures have equal bytes;
9. write exactly one Initial record before reporting `Ready(0)`;
10. select and report typed failures reachable from those paths; and
11. disable and dispose idempotently so later callbacks are inert and the
    sink is closed at most once.

The task retains the existing Task 4.1 `HookToken`, `UpdateDirective`,
`GateSample`, `CaptureException`, and `IPassiveReporter` contracts. It adds
`IPassiveUpdateObservation` and `PassiveUpdateBoundary` because their complete
ordering is part of this slice.

### 3.2 Deferred production scope

The following items must not appear in Task 4.2 merely as future scaffolding:

- `completedInputs` and pending-attempt state;
- `PendingInput`, `PendingAccepted`, and `PendingMovementScheduled`;
- manual-attempt creation and cleanup;
- manual `ProcessInput` or Undo correlation state;
- settled Step emission;
- expected-input End completion;
- Restart and state-set lifecycle hooks; and
- partial-method seams used only by Tasks 5.1--5.3.

The corrected executable plan will move each item into the first downstream
task whose RED tests exercise it. If a small shared field must be added to an
existing Task 4.2 class in Task 5.1, Task 5.1 may modify that file explicitly;
preserving a no-touch downstream diff is not a reason to violate TDD.

The fake sink must still implement the complete existing `ITraceSink`
interface. Its Step and End methods are interface stubs, not permission to add
driver Step or End behavior in Task 4.2. Tests require those collections to
remain empty.

## 4. Initial driver behavior

### 4.1 Preparation, activation, and teardown

`Prepare` is one-shot. It accepts one valid Run record, writes it before any
reporter call, and records the run identity and UTC start only after the write
succeeds. A Run write failure selects marker-only `trace_io_failed` behavior
without claiming a durable Error record.

`Activate` is one-shot and succeeds only after preparation while the driver is
neither disabled, disposed, nor terminal. It enters `AwaitGame`. A second
prepare or activation attempt is inert and returns false.

`Disable` makes subsequent observation callbacks inert. `Dispose` is
idempotent and owns at most one sink-close attempt. Later callbacks do not
write records or markers. The supported integration contract serializes game
observation, controller teardown, and `Dispose` on Unity's main thread after
the controller has disabled and unpatched the driver. A deliberately
concurrent close-versus-active-write race is outside Task 4.2's call contract;
the design does not add a monitor around sink or reporter calls. Interlocked
state remains required for one-shot preparation/activation, terminal choice,
directive stages, token consumption, disable/dispose, and close ownership.

Task 5.3 remains responsible for the complete competing-fault and successful
terminal lifecycle matrix. Task 4.2 nevertheless proves one terminal winner,
at most one failure-marker attempt, one close attempt, and inert late
callbacks for every failure it can originate.

### 4.2 Ordered update boundary

One normal update callback follows this exact sequence:

```text
TryGetState (begin identity)
NowSeconds
PassiveDriver.BeginUpdate
VerifySavePath
TryGetState (verified identity)
PassiveDriver.AuthorizeUpdate
IsQuiescent, when authorized and eligible
Capture, only when authorized, eligible, and quiescent
UtcNow
PassiveDriver.CompleteUpdate
```

No gate or capture operation may occur before save-path and identity
authorization. A false path result faults with `save_path_changed` and skips
the identity reread, gate, and capture. A thrown `CaptureException` maps to
`capture_failed`; another observer exception maps to `observer_exception`.
No observer exception crosses the boundary.

An authorization or completion failure consumes the outstanding directive at
most once. A stale, foreign, inactive, duplicate, or out-of-order directive
cannot authorize capture. The test seam exposes enough directive metadata to
prove that a replacement rebase changes both epoch and frame metadata, rather
than merely changing the driver's public frame counter.

### 4.3 Initial epochs and replacement

The first usable state starts an initial epoch. The first counted update in an
epoch has `currentFrames == 1`. A state that becomes unusable before Initial
returns the driver to `AwaitGame`. A state that becomes usable only on the
verified reread starts a frame-one epoch on that callback.

A different verified state before Initial starts a new epoch on that same
callback and completes the callback as `NotInspected`. Replacement resets:

- the neutral flag;
- the candidate signature;
- the most recent complete capture;
- the monotonic epoch start;
- current frames to one for that callback; and
- all initial identity state belonging to the old epoch.

The authorized directive is rebased to the new epoch and frame one, with gate
inspection and post-sample timeout disabled for the replacement callback.
Neither an old neutral poll nor an old candidate may leak into the new epoch.

### 4.4 Debounce

A physical neutral result enables later eligible samples in the current
epoch. A cardinal physical result clears both neutral eligibility and the
candidate. `NotInspected` and `NonQuiescent` samples break consecutive-pair
continuity. `Capture` is unreachable for a nonquiescent sample.

Two captures settle only when `CaptureSignature.Compute` produces equal bytes
on two distinct eligible update callbacks. The test oracle must prove both
directions:

- distinct `CaptureRecord` objects with equal field values do settle; and
- consecutive valid captures with unequal signatures do not settle until a
  later equal consecutive pair appears.

Object reference equality is not a substitute for signature equality, and
the mere existence of two captures is insufficient.

### 4.5 Deadlines

Each update first computes `nextFrames` and elapsed monotonic time. If
`nextFrames` is greater than the frame maximum or elapsed time is greater than
the time maximum, it faults before path verification, gate inspection, or
capture. The reported pre-capture frame count is capped at the configured
maximum.

At exactly the frame or time limit, the callback is still authorized and may
inspect one sample. A matching second sample wins. If that exact-boundary
sample does not complete the pair, `initial_settle_timeout` is selected after
the sample. Tests cover successful and unsuccessful exact-frame and exact-time
boundaries, plus both frame and time pre-overruns.

Replacement resets the deadline origin. A test places the replacement beyond
the old epoch's remaining budget but inside the new epoch's budget to prove
that the new monotonic start governs.

## 5. Error and record policy

Task 4.2 uses only the closed schema-v1 error table. Its tests exercise every
exception source introduced by this task: initial Run write, begin-state read,
monotonic time, path verification, verified-state read, quiescence, capture,
UTC acquisition, Initial write, Ready reporting, Error write, sink close, and
failure/diagnostic reporting.

The tests distinguish capture failures, generic observer failures,
record-too-large failures, and trace I/O failures. They prove:

- one winning terminal code;
- at most one Error record;
- Error before close before the failure-marker attempt when Error write and
  close both succeed;
- a `trace_io_failed` terminal marker, when reporting itself succeeds, if
  Error write or close fails;
- no false durable-error claim after a sink failure;
- permission for a successfully flushed Error record to remain on disk when a
  later close fails, while still forbidding a marker that claims its original
  code as the authoritative terminal result;
- `last_capture` is the most recent complete bounded capture in the current
  epoch; and
- replacement clears the old epoch's `last_capture` before a later fault.

No sink or reporter call occurs while a monitor is held. The intended driver
does not require a monitor for main-thread observation state.

## 6. Test design

The original eight registration names are not normative. The amended plan may
split cases when that makes each failure oracle clearer. Every production
method introduced by Task 4.2 must have a RED test that failed because the
surface or behavior was absent.

The test matrix includes at least:

1. constructor, Prepare, Activate, Disable, Dispose, and late-callback rules;
2. exact boundary call order and authorization ownership;
3. exception classification and containment at every boundary operation;
4. pre-epoch neutral isolation;
5. equal-value/distinct-object and unequal-signature debounce;
6. `NotInspected`, `NonQuiescent`, and cardinal continuity breaks;
7. replacement rebase metadata plus every epoch reset;
8. first-unusable/second-usable and first-usable/second-unusable callbacks;
9. exact frame/time success and unsuccessful post-sample timeout;
10. frame/time pre-overrun ordering and capped error fields;
11. Initial-record-before-Ready ordering and Ready failure behavior; and
12. terminal record/close/marker cardinality for reachable failures.

Controlled mutation evidence must prove the tests reject, at minimum:

- accepting any two captures;
- using capture object identity;
- retaining a candidate across `NotInspected`, `NonQuiescent`, or cardinal
  input;
- retaining neutral, candidate, deadline origin, or `last_capture` across
  replacement;
- rebasing a replacement directive to frame zero or the old epoch;
- capturing a nonquiescent state;
- inspecting before path and identity authorization;
- removing exact-boundary post-sample timeout;
- removing frame pre-overrun or frame capping;
- collapsing `CaptureException` into generic observer failure;
- reversing Initial/Ready or Error/close/failure-marker order; and
- permitting a duplicate terminal record or close.

Every mutant is applied independently, killed at its named behavioral oracle,
and reversed before its evidence is accepted. The controller independently
replays the mutation set from the committed implementation.

## 7. Executable-plan and repository gates

The Task 4.2 plan rewrite must follow the hardened Task 4.1 evidence model,
scaled to this slice:

- pin the merged execution base, plan, written design, generated brief, and
  current source/test hashes in both the report and progress ledger;
- classify RED by an exact compiler-diagnostic multiset, with tests and
  registry present, production absent, an empty index, and exact allowed
  status;
- begin every multi-command shell block with `set -euo pipefail`;
- capture stderr with stdout and reject compiler, warning, timeout, SDK,
  assets, restore, permission, and infrastructure failures unless a specific
  compiler failure is the named RED;
- build the unit project and net35 Core project sequentially with
  warnings-as-errors and forced recompilation (`-t:Rebuild`), never relying on
  incremental outputs from a prior failed build;
- run the focused cohort and complete harness from the freshly built unit
  artifact with `--no-build`, requiring exact ready stdout;
- use `--no-restore` for every dotnet command and `UV_OFFLINE=1` for every
  `uv` command;
- assert exact modified/untracked scope before staging, exact staged scope
  before committing, and clean index/worktree/diffs after committing;
- stage only the enumerated Task 4.2 paths and reject any pre-existing staged
  path;
- make one named implementation commit after RED, GREEN, mutation, and
  precommit gates pass;
- bind independent review and controller replay to the exact implementation
  commit and source hashes; and
- run a final postcommit gate that repeats focused/full/net35 verification and
  repository identity checks.

The plan amendment is a separate documentation commit made before product
RED. The generated brief is controller-owned ignored evidence and is not
regenerated by the implementer.

Because this is now a descendant documentation commit, the plan amendment may
also perform the already-approved cleanup of the ten Task 4.1 fixed-string
quote literals. That cleanup is recorded separately from Task 4.2 changes and
does not alter Task 4.1's historical commits, reviews, or mutation evidence.

## 8. Review and completion

Before implementation dispatch, independent reviewers must approve:

1. product/spec completeness and the scope transfer into Tasks 5.1--5.3;
2. test discrimination and mutation coverage;
3. shell/gate fail-fast behavior, forced rebuilds, evidence freshness, and
   exact repository scope; and
4. C# 7.3, CLR v2, and net35 compatibility.

Task 4.2 is complete only when strict RED precedes production, focused and full
behavioral harnesses pass, forced unit/net35 builds have zero warnings and
zero errors, every implementer mutation and controller replay fails at its
named oracle, the exact task commit receives clean specification and quality
reviews, and the final repository gate passes from that commit.

All work remains offline. This design does not authorize a game launch, GUI,
deployment, dependency restore, installed configuration change, save access,
or real trace capture.
