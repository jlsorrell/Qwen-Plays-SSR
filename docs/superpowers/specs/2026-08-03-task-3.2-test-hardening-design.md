# Task 3.2 Sink Test Hardening Design

**Date:** 2026-08-03

**Status:** Approved conversational design; written specification pending final user review

## Purpose

Task 3.2 completes `NdjsonTraceSink` by adding LF-terminated record writes,
per-record flushes, a 128 MiB trace budget, failure-state transitions, and
single-owner close behavior. The planned production state machine is correct,
but the three dormant Task 3.2 tests contain false positives and leave three
public writer methods entirely unexecuted.

This amendment hardens the existing three tests before implementation. It does
not change the production contract, add a registration, change a manifest
identity, or broaden runtime scope.

## Preflight findings

The original dormant tests do not prove all behavior claimed by the Task 3.2
plan:

1. `WriteStep`, `WriteEnd`, and `WriteError` are never called through the sink.
2. The only partial-write case is a positive short write followed by zero, so
   an implementation that rejects every short write can pass.
3. The cumulative-budget case still passes if LF bytes are omitted from the
   accounting.
4. Write and flush terminality still pass if `Fail()` is deleted, because the
   injected failure remains armed for the second call.
5. The budget test cannot distinguish a terminal sink from an open sink whose
   exhausted budget rejects every later record.
6. Flush count alone does not prove that a flush occurs after the complete LF
   terminated line.
7. The fake rejects an over-reported write count before the sink can exercise
   its own invalid-progress branch.
8. No sink test proves that encoding and record-size failures leave the sink
   reusable.
9. No test proves that exactly one best-effort close remains legal after a
   write, flush, invalid-progress, or budget failure.
10. Close tests do not pin the underlying close count after a failed close or
    preserve the injected exception identity.

Three independent read-only preflight audits agreed that the exact planned
production implementation is otherwise sound, overflow-safe, atomic-create
preserving, C# 7.3 compatible, and net35 API compatible.

## Invariants

The hardening must preserve all of the following:

- The Task 3.2 production body remains the exact state machine already planned.
- The sink cohort retains exactly six registrations in the frozen order.
- The three Task 3.2 identities remain exactly:
  - `records use LF and flush`
  - `bounds and write failures are terminal`
  - `close ownership is single use`
- `TestSupport.cs` and its frozen 82-identity catalog do not change.
- Temporary `Program.cs` counts remain exactly `protocol=4`, `encoding=5`, and
  `sink=6`.
- Successful harness stdout remains exactly `SSR oracle unit harness ready`.
- Product implementation scope remains exactly `NdjsonTraceSink.cs`,
  `TraceSinkTests.cs`, and `Program.cs`.
- All work remains offline. No game launch, deployment, package restore,
  network access, installed configuration mutation, or save mutation is
  authorized.

## Test-output seam

`FakeTraceOutput` remains the sole general output seam and gains only the
observability needed by the approved tests:

- `FlushByteCounts` records `Bytes.Count` at entry to every flush attempt.
- Positive values in `WriteCounts` continue to request deterministic partial
  writes.
- Zero continues to represent no progress.
- A dedicated `ReturnTooMany` flag returns `count + 1` without copying bytes,
  allowing the sink—not the fake—to classify over-reported progress.
- Normal configured writes copy only the reported valid slice.
- Existing write, flush, and close exception injection and counters remain.

Recording the byte count at flush entry proves ordering. A successful flush
snapshot must equal the cumulative size through that record's LF, not merely
the number of times `Flush()` happened.

## Successful record flow

`RecordsUseLfAndFlush` will exercise all five public record methods in wire
order:

1. `WriteRun(ProtocolSamples.Run)`
2. `WriteInitial(ProtocolSamples.Initial)`
3. `WriteStep(ProtocolSamples.Step0)`
4. `WriteEnd(ProtocolSamples.End)`
5. `WriteError(ProtocolSamples.Error)`

The first line is fragmented with two positive configured writes before the
fake resumes full writes. This proves positive short writes are retried to
completion.

The test independently assembles the expected stream by appending each
`CanonicalJson.EncodeX` result followed by one literal byte `0x0a`. After each
public call it checks the complete cumulative bytes. At the end it requires:

- exact equality with all five encoded lines;
- exactly five flush calls;
- exact flush snapshots at the five cumulative LF boundaries;
- no UTF-8 BOM prefix; and
- no missing, duplicated, reordered, CR, or trailing bytes.

Because the expected stream contains only canonical encoder bytes plus literal
LF, exact equality also proves LF rather than CRLF and makes an extra final
delimiter observable.

## Bounds and terminal failures

`WriteFailuresAreTerminal` is divided into deterministic helpers so every
state transition has a distinct assertion label.

### Cumulative budget and LF accounting

Let `runBytes` be the encoded Run length and construct the sink with
`maxTraceBytes = 2L * runBytes`.

- The first Run plus LF fits.
- A second Run plus LF must fail before any additional output or flush.
- If either LF is omitted from accounting, both JSON payloads fit exactly and
  the second call incorrectly succeeds.
- After the failure, an End line would fit the real remaining byte budget
  (`runBytes` is 302 and the End payload is 142 in the pinned fixture), but the
  terminal sink must reject it without changing bytes or flush counts.

This single construction independently distinguishes LF accounting from the
`Failed` transition. It also pins that a rejected line performs no partial
write.

### Invalid progress

Two separate sinks cover the invalid-progress boundaries:

- A positive short write followed by zero must raise `TraceIoException`, enter
  `Failed`, and never flush the incomplete line.
- `ReturnTooMany` must make the sink reject a result greater than the requested
  remainder, enter `Failed`, and write no bytes.

After each case, the fault stimulus is removed or exhausted and a valid record
must still be rejected. Each failed sink must then permit exactly one close;
the second close must be rejected without another underlying close attempt.

### Injected write and flush failures

For write and flush exceptions separately, the test will:

1. inject a distinct `IOException` instance;
2. require a `TraceIoException` whose `InnerException` is that exact instance;
3. snapshot the output bytes, flush count, and flush boundaries;
4. clear the injected exception;
5. require a later valid record to remain rejected with no output changes; and
6. require exactly one legal best-effort close followed by a rejected retry.

Clearing the stimulus before the second write ensures the test observes sink
state rather than the same environmental exception twice.

### Encoding failures remain reusable

Two independent open sinks prove that failures before `WriteEncoded` do not
poison the session:

- An Initial record containing an unpaired surrogate must raise
  `CanonicalEncodingException`, emit no bytes or flush, and then permit a valid
  record.
- An otherwise valid Error record one byte beyond the 16 MiB line boundary
  must raise `RecordTooLargeException`, emit no bytes or flush, and then permit
  a valid record.

The oversized case uses the already pinned boundary arithmetic: zero-length
Error JSON is 421 bytes, accepted `raw_save` length is 16,776,794, and length
16,776,795 is one byte over after LF. It adds one fixed, bounded allocation
instead of adding a production testing seam.

## Close ownership

`CloseIsSingleUse` retains the normal and failing-close paths and strengthens
their observable consequences:

- Normal close performs exactly one underlying close, rejects a retry, leaves
  the underlying count at one, and rejects every later record.
- An injected close exception is wrapped in `TraceIoException` with identical
  `InnerException`, performs exactly one underlying close attempt, rejects a
  retry without incrementing the count, and rejects every later record.
- The failure helpers above additionally prove the `Failed -> Closing ->
  FailedClosed` path by allowing one close after budget, invalid-progress,
  write, and flush failures.

## Controlled mutation proof

Every mutant is applied alone after provisional GREEN, run only against the
sink cohort with `--no-restore`, and required to fail at its predetermined
registration and assertion. The exact inverse patch is applied immediately.
No mutant may be staged. Hashes, index, and tracked status must return to the
reviewed pristine values after every inverse.

The executable plan will include mutants for:

1. making one of `WriteStep`, `WriteEnd`, or `WriteError` a no-op;
2. omitting the literal LF write;
3. flushing before the LF write;
4. performing only one output write instead of retrying a positive short write;
5. calculating `lineBytes` without `+ 1L`;
6. deleting `Fail()` from the cumulative-budget branch;
7. deleting `Fail()` from the write-exception branch;
8. deleting `Fail()` from the flush-exception branch;
9. removing the `written > remaining` invalid-progress check;
10. forbidding `Close()` when the state is `Failed`;
11. poisoning the sink after `CanonicalEncodingException`;
12. poisoning the sink after `RecordTooLargeException`; and
13. permitting an underlying close retry after a completed or failed close.

The plan amendment must state the exact expected registration and assertion
text for each mutant. A generic nonzero exit is insufficient evidence.

## Non-goals

- No production behavior beyond the already approved Task 3.2 state machine.
- No new public or internal production seam.
- No new test registration or manifest identity.
- No change to canonical encoding, protocol DTOs, capture signatures, driver
  behavior, plugin integration, runtime instrumentation, or Python validation.
- No additional constructor/null-argument matrix; those simple planned guards
  remain subject to code review and net35 compilation, while this amendment
  focuses on load-bearing write, bound, failure, and ownership behavior.
- No game launch or runtime acceptance work.

## Acceptance criteria

The design is satisfied only when:

- all five writer methods produce the exact cumulative LF-delimited bytes;
- each complete record is flushed only after its LF;
- positive partial writes complete successfully;
- zero and over-reported progress fail terminally;
- the file budget counts LF, rejects before output, and becomes terminal;
- cleared write/flush stimuli cannot make a failed sink writable again;
- encoding and record-size failures leave an open sink reusable;
- one close remains legal after each sink failure and no close is attempted
  twice;
- all thirteen controlled mutants are rejected at their named assertions;
- focused, full, net35, diff, hash, index, and scope gates pass; and
- independent review and controller replay both approve the committed result.
