# Task 2.2 Capture-Signature Test Hardening Design

## Context

Task 2.2 implements the internal stability signature used by the passive
driver to compare complete captures. The implementation committed in
`9cc342ad9c866366544efe8885a64af7fc482a89` matches the authoritative wire
design: all twelve capture fields are encoded in JSON field order, each value
is preceded by a four-byte unsigned big-endian byte length, and the resulting
stream is hashed with SHA-256.

The pre-acceptance contract audit found defects in the exact test body, not in
the production implementation:

- the two records described as an unframed concatenation collision do not
  actually concatenate to the same bytes;
- comparing one multibyte record only with `InitialCapture` proves merely that
  at least one changed field affects the result, not that every field and its
  position are bound;
- malformed-Unicode coverage reaches only `raw_save`, although `level`,
  `lost_reason`, and `display_name` are also unrestricted strings; and
- the line-boundary test finds a known linear boundary with roughly twenty-five
  large encodes, creating avoidable allocation pressure.

This amendment strengthens only `CaptureSignatureTests.cs`. Production code,
fixtures, the five-test encoding manifest, and all wire behavior remain
unchanged.

## Approaches Considered

### 1. Deterministic vector matrix and focused mutation proofs — selected

Use genuine collision inputs, externally calculated fixed digests, one-field
input variants, complete unrestricted-string surrogate coverage, and direct
line-bound arithmetic. Prove the new assertions with a small set of temporary
production mutants, restoring the exact production hash after each run.

This gives independent byte-level anchors without reproducing the hashing
algorithm inside the C# tests.

### 2. Minimal assertion repair

Replace only the false collision pair, hard-code the existing multibyte
digest, and add three surrogate cases. This is smaller, but it leaves blind
spots for field omission, substitution, and order mistakes among repeated
boolean and integer values.

### 3. A reference signature implementation in the test assembly

Implement the framing and hashing algorithm a second time in the tests and
compare outputs over many records. This offers broad coverage, but the test
oracle can repeat the production bug and makes the test harder to audit than a
small set of externally calculated constants.

## Signature Test Design

The existing registration names remain exactly:

- `capture signature is exact`
- `record line limit includes LF`

No registration is added, removed, renamed, reordered, or moved to another
cohort.

### Genuine framing collision

The first assertion compares two valid captures whose values are identical
except for the first two string boundaries:

- left: `raw_save="a"`, `state_identity="12"`, `level="c"`;
- right: `raw_save="a1"`, `state_identity="2"`, `level="c"`.

All remaining fields are identical. Without per-value lengths, both inputs are
exactly:

```text
a12cfalsefalsefalsefalse000
```

Their correctly framed signatures must differ. Placing this assertion first
also makes a temporary no-prefix mutant fail specifically at the collision
claim.

### Externally calculated fixed vectors

The existing `InitialCapture` digest remains pinned:

```text
c870e028a5a526efc0e8af5f78bcea1ff89198b29b16a875715c65f78649c6b7
```

Two additional complete vectors pin multibyte UTF-8, signed and multi-digit
scalar text, and field positions. Expected digests are hard-coded; the C# test
does not reconstruct the framing algorithm.

Vector A:

```text
raw_save="é/雪"
state_identity="-2147483648"
level="x"
overworld=true
won=false
returning=true
have_ever_cooked_all=false
lost_reason=""
display_name="z"
sausages_cooked=2147483647
movement_count=0
pushes_to_try=0
SHA-256=6e924d4765c53622d9f734126cdf960fd525cc8a491068fe606606fb0833eac6
```

Vector B:

```text
raw_save="r2"
state_identity="42"
level="l2"
overworld=false
won=true
returning=true
have_ever_cooked_all=false
lost_reason="lost2"
display_name="display2"
sausages_cooked=1
movement_count=2
pushes_to_try=3
SHA-256=2ad1bf134d02a71476f3b7c220d817700079c10051607ab2796a2126406dde8d
```

Across vectors A and B, the four boolean positions have distinct two-vector
patterns: `10`, `01`, `11`, and `00`. Vector B also gives the three integer
positions distinct values. A swap or substitution among positions that is
invisible in one vector is visible in the other.

### Every field affects the signature

Create one valid baseline capture with non-null values. Construct twelve
variants, changing exactly one field in each variant while keeping all other
fields fixed. Each variant's signature must differ from the baseline. This
directly detects omission of any capture field without adding registrations or
duplicating production framing logic.

### Strict Unicode for every reachable unrestricted string

Construct four otherwise-valid captures containing one unpaired high
surrogate in exactly one of these fields per case:

- `raw_save`;
- `level`;
- `lost_reason`;
- `display_name`.

Each call to `CaptureSignature.Compute` must throw
`CanonicalEncodingException`. `state_identity` is not included because the
DTO constructor already restricts it to canonical signed `Int32` text, making
an invalid surrogate unreachable at the signature boundary.

## Exact Line-Boundary Design

The boundary record uses only literal ASCII `x` bytes in `raw_save`, so every
additional character increases the encoded line by exactly one byte. The
zero-length record is exactly 421 encoded bytes. Therefore:

```text
accepted_raw_save_length = 16,777,216 - 1 LF - 421 = 16,776,794
```

The test performs one small baseline encode, one exact-bound encode, and one
one-byte-over encode:

- `16,776,794` raw-save bytes produce `16,777,215` JSON bytes and are accepted
  because the added LF reaches exactly `16,777,216`;
- `16,776,795` raw-save bytes are rejected with `RecordTooLargeException`.

This preserves the same semantic proof while removing the binary-search
allocation loop.

## Mutation Evidence

The follow-up test fix must prove the hardened assertions against temporary,
one-at-a-time production mutants:

1. omit the four-byte prefix feed, requiring the genuine-collision assertion
   to fail;
2. omit the `display_name` feed, requiring its one-field variant to fail;
3. swap `overworld` and `returning`, requiring vector B's fixed digest to fail
   even though vector A has `true` in both positions;
4. encode `display_name` permissively, requiring the last surrogate case to
   fail;
5. ignore the LF in the line limit, requiring the one-byte-over assertion to
   fail; and
6. reject `>=` the limit, requiring the exact-bound assertion to fail.

Each mutant is applied and reverted with an exact inverse patch. After every
reversion:

- `CaptureSignature.cs` must have SHA-256
  `335c500506354defba8331eddf1492568797c97170ee1754d319fcf97e9a9d54`;
- `CanonicalJson.cs` must have SHA-256
  `7e6e50f22aae26bad26f26f6fd248d32f08e116bf2598dc572eff2000151826c`;
- the git index must be empty; and
- no mutant may be committed or staged.

## Scope and Acceptance

The implementation fix changes only
`oracle/plugin/tests/CaptureSignatureTests.cs`. `CaptureSignature.cs`,
`CanonicalJson.cs`, `Program.cs`, fixtures, and registration identities remain
byte-identical.

Final acceptance requires:

- the encoding cohort to print exactly `SSR oracle unit harness ready`;
- the compile-only net35 Core build to report zero warnings and zero errors;
- `git diff --check` and tracked worktree status to be clean after the
  test-only follow-up commit;
- an independent scoped review to confirm every audit finding is addressed;
  and
- no game launch, deployment, restore, network access, configuration write,
  or save mutation.
